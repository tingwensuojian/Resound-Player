# 本地歌词匹配与标签补全复用说明

## 概述

当前项目已经落地了一套可复用的“**本地歌曲云端匹配 + 文件缺失标签补全 + 状态可视化**”链路。

这套能力不是单一弹窗，而是由三层共同组成：

1. `云端匹配层`
   负责把本地歌曲和云端歌曲建立关联，并缓存后续写入所需的完整元信息。
2. `文件写入层`
   负责只向本地音频文件写入“缺失字段”，不覆盖用户已有标签。
3. `状态展示层`
   负责让本地歌曲列表、歌手、专辑、目录、歌单、播放页、迷你模式都能看懂当前歌曲处于什么状态。

目前默认策略固定为：

- 只补缺失，不覆盖已有
- 先匹配，再写入
- 写入后可追踪状态
- 支持回滚本次补写内容

---

## 适用范围

当前已支持：

- 本地歌曲云端匹配
- 云端歌词缓存
- 云端封面缓存
- 单曲标签补全预览
- 单曲标签手动编辑后写入
- 单曲标签写入
- 单曲标签回滚
- 全本地模块状态可视化
- 行内更多操作快捷入口

当前写入格式：

- `mp3`
- `flac`
- `m4a`
- `aac`

格式实现现状：

- `mp3` 走 `node-id3`
- `flac` 走 `flac-tagger`
- `m4a/aac` 走 `@yortyrh/tagpilot-lib`

当前 V1 核心可写字段：

- 标题 `title`
- 歌手 `artists`
- 专辑 `album`
- 专辑歌手 `albumArtist`
- 风格 `genre`
- 年份 `year`
- 碟序 `discNo`
- 曲序 `trackNo`
- 歌词 `lyrics`
- 封面 `artwork`

其中 `m4a/aac` 当前字段映射说明：

- 标题 -> MP4 标题标签
- 歌手 -> MP4 artists
- 专辑 -> MP4 album
- 专辑歌手 -> MP4 albumArtists
- 风格 -> MP4 genre
- 年份 -> MP4 year
- 曲序 -> MP4 track.no
- 碟序 -> MP4 disc.no
- 普通歌词 -> 当前写入可回读 `comment` 字段
- 封面 -> front cover image

## 三、写入结果如何即时刷新 UI

这是当前实现里非常关键的一层。

如果只写文件和数据库，不同步前端内存，页面会继续显示旧歌手、旧专辑、旧封面、旧分类结果。

因此现在写入后，会立刻同步三类对象：

1. `state.tracks`
2. `state.playlists[*].tracks`
3. `playerStore.state.currentTrack / playerStore.state.playlist`

实现位置：

- [localMusic.ts](/Users/sangxuesheng/Downloads/gemini音乐/src/stores/localMusic.ts)

关键方法：

- `writeMetadata(track)`
- `applyMetadataWriteResult(track, result)`
- `refreshTrackCover(track)`
- `resolveTrackCover(track)`

### 刷新内容

写入后会即时更新：

- 标题
- 歌手
- 专辑
- 专辑歌手
- 风格
- 年份
- 碟序
- 曲序
- 歌词状态
- 封面

还会同步更新：

- 本地歌单中引用到该歌曲的对象
- 当前播放中的本地歌曲
- 播放队列中的同一首本地歌曲

### 为什么歌手页 / 专辑页会自动重新分类

因为 `artistList` 和 `albumList` 是基于 `state.tracks` 的 `computed` 聚合结果。

只要 `tracks` 里的 `artist / album / coverUrl` 被即时更新：

- 本地歌手分类会立刻重算
- 本地专辑分类会立刻重算
- 播放页封面和标题也会立刻变

## 五、数据库表职责

### `local_lyric_matches`

职责：

- 保存本地歌曲与云端歌曲的匹配关系
- 缓存后续可写入的完整云端元信息

不要把它再理解成“只存歌词匹配”的表。

它现在本质上是：

- 匹配缓存表
- 标签写入缓存表

### `file_metadata_state`

职责：

- 保存单文件写入状态
- 保存写入指纹
- 保存已写过哪些字段
- 保存回滚快照
- 保存最后一次写入/回滚结果

它是后续批量补全、增量补全、断点恢复的底座。

## 六、前端复用方式

如果后面要在新入口接入“本地匹配 + 标签补全”，建议按下面顺序接。

### 方案 A：复用现有弹窗

推荐场景：

- 本地歌曲列表
- 播放页
- 右键菜单
- 本地歌单详情页

做法：

1. 准备一个本地 track 对象，至少要有：
   - `id`
   - `path`
   - `title` 或 `name`
   - `artist`
   - `album`
   - `coverUrl`
   - `source: 'local'`
2. 打开 [LocalLyricMatchDialog.vue](/Users/sangxuesheng/Downloads/gemini音乐/src/components/LocalLyricMatchDialog.vue)
3. 在匹配成功后，通过其内部按钮继续打开 [LocalMetadataWriteDialog.vue](/Users/sangxuesheng/Downloads/gemini音乐/src/components/LocalMetadataWriteDialog.vue)

优点：

- 复用完整交互
- 自动带封面预览
- 自动带状态说明
- 自动带成功反馈

### 方案 B：只复用标签补全弹窗

推荐场景：

- 已经存在匹配关系，不需要再搜索云端歌曲

做法：

1. 保证当前 track 已经有 `local_lyric_matches` 记录
2. 直接打开 `LocalMetadataWriteDialog`

注意：

- 如果没有匹配缓存，`previewMetadataWrite` 会失败
- 这是预期行为，因为写入阶段不做实时云端补拉

## 七、推荐接入步骤

新增一个“补全缺失标签”入口时，建议照这个顺序：

1. 先确认当前曲目是本地歌曲，且存在 `path`
2. 先读 `getMetadataStatus(track)` 决定按钮文案
3. 若无匹配关系，先打开 `LocalLyricMatchDialog`
4. 若已有匹配关系，可直接打开 `LocalMetadataWriteDialog`
5. 写入成功后，不要手动重扫目录
6. 直接依赖 `localMusicStore.writeMetadata()` 的内存同步结果刷新页面

## 八、当前交互表现

### 匹配成功后

- 匹配弹窗左侧会显示当前选择歌曲的封面预览
- 当前匹配区会显示：
  - 云端匹配状态
  - 文件标签状态
- 本地歌曲如果没有内嵌封面，会立即回落到匹配缓存封面

### 打开标签补全弹窗时

- 会先显示当前文件状态
- 会先把云端建议值填入可编辑表单
- 会显示将写入字段
- 会显示将跳过字段与原因
- 用户编辑表单后，预览区会实时重算

### 写入成功后

- 会显示成功摘要，例如：
  - `已写入：封面、专辑、年份、歌词`
- 会同步刷新本地列表、分类、播放页、歌单内存对象

### 云端歌词写入说明

当前云端歌词已经接入标签写入主链路。

写入前提：

- 当前文件本身没有歌词
- 匹配缓存里存在 `cloudLyrics` 或 `cloudSyncedLyrics`

写入行为：

- 补全弹窗会先把云端歌词预填到“歌词”编辑框
- 用户可以直接写入，也可以手动修改后再写入
- 成功摘要里会显示 `歌词`

注意：

- 之前出现过“云端歌词未写入”的问题，根因是预览结果未把 `lyrics` 回传给前端
- 当前已修复，现版本会正确把云端歌词预填并写入
- 对 `m4a/aac` 而言，当前普通歌词会落到可回读注释字段，先保证“能写入、能再次识别”，不直接承诺逐字歌词盒子兼容

## 九、当前限制

当前仍有限制，后续复用时要知道：

1. 当前稳定支持 `mp3/flac/m4a/aac`
2. 仅支持单曲写入，不支持批量任务 UI
3. 写入来源依赖本地缓存的匹配元信息，不在写入期实时请求云端
4. 默认没有“覆盖已有”模式
5. 高级歌词字段（逐字/翻译/音译）虽然缓存已准备，但 V1 主写入路径仍以普通歌词为主
6. 当前封面仍以云端缓存封面为主，尚未开放用户手动替换本地图片文件作为封面
7. `m4a/aac` 的普通歌词当前写入到可回读的注释字段，后续如需逐字歌词或更细分的 MP4 歌词盒子，需要单独扩展
8. `m4a/aac` 本轮已完成静态链路接入，但真实样本的端到端回写验证还需要继续补自动化或固定测试样本
