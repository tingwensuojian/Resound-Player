# 迷你模式实现说明

## 概述

当前迷你模式已经从“单窗口缩放切换”重构为“主窗口 + 迷你窗口”的双窗口方案。

目标是解决 macOS 下退出迷你模式时主窗口黑屏闪一下的问题。根因已经确认不是前端过渡动画缺失，而是同一个 `BrowserWindow` 在 `340×70` 迷你尺寸与主窗口大尺寸之间反复重设时，Electron/macOS 窗口表面重建导致的黑场。

现版本通过以下方式规避该问题：

- 主窗口 `mainWin` 始终保持正常应用窗口身份
- 进入迷你模式时隐藏主窗口，不再把主窗口缩成迷你条
- 新建独立 `miniWin` 承载迷你播放条 UI
- 播放内核只运行在主窗口
- 迷你窗口只接收播放快照、发送播放命令，不创建第二套音频实例

这条链路已经满足当前目标：

- 迷你模式可以正常进入
- 迷你模式可以正常退出
- 退出时主窗口不再经历“缩放回大窗口”的黑屏闪烁
- 迷你模式 UI 规格维持原样，没有重新设计

## 架构全景

```text
主窗口 mainWin
  ├─ 加载 index.html
  ├─ 承载完整主应用 UI
  ├─ 持有唯一 Audio / audioEngine / runtime
  ├─ 执行所有播放命令
  └─ 向主进程发布 playback snapshot

迷你窗口 miniWin
  ├─ 加载 mini.html
  ├─ 仅挂载 MiniPlayBar
  ├─ 初始化 uiStore / playerStore / userStore
  ├─ 不创建 Audio / audioEngine
  ├─ 接收 playback snapshot 渲染 UI
  └─ 通过 IPC 向主窗口发送播放控制命令

主进程 electron/main.js
  ├─ 进入迷你模式时：
  │   ├─ 保存 mainWin 之前的窗口状态
  │   ├─ 创建并显示 miniWin
  │   └─ 隐藏 mainWin
  ├─ 退出迷你模式时：
  │   ├─ 关闭 miniWin
  │   ├─ 恢复 mainWin 的尺寸 / 位置 / 最大化 / 全屏状态
  │   └─ 显示 mainWin
  ├─ 转发 playback command: miniWin -> mainWin
  └─ 转发 playback state: mainWin -> miniWin
```

## 关键设计决策

### 1. 不再复用同一个 BrowserWindow 做迷你模式

这是这次改造的核心前提。

旧方案的问题是：

- 进入迷你模式时把主窗口改成 `340×70`
- 退出迷你模式时再恢复到原本大窗口尺寸
- macOS 下这个恢复动作会触发表面重建，出现黑屏

因此当前方案明确改为：

- 主窗口只做主窗口
- 迷你窗口只做迷你窗口

### 2. 主窗口是唯一播放宿主

播放内核只能存在一份，否则会出现：

- 两个窗口都创建 `Audio`
- 两边播放状态冲突
- 媒体会话、音量、播放进度不同步
- 命令源和状态源不一致

因此当前规则是：

- `main` 角色窗口可以初始化播放器 runtime
- `mini` 角色窗口禁止初始化 runtime
- 迷你窗口只能消费快照并发送命令

### 3. 迷你模式 UI 保持原规格，不做重新设计

当前双窗口方案不是新的 UI 设计方案，而是现有迷你模式 UI 的承载方式改造。

保持不变的内容包括：

- 紧凑态窗口尺寸 `340×70`
- 播放列表展开高度 `340×360`
- 封面、歌名、控制按钮布局
- 点击封面 / 标题恢复主窗口并打开扩展播放页的交互意图
- 拖拽区域和按钮区域划分

## 播放状态同步与统一播放事务

迷你窗口只消费主窗口发布的 `PlaybackSnapshot`，不直接播放音频。为了避免混合队列下出现“迷你窗口封面已变，但主窗口 audio 仍播放旧歌”的状态错位，主窗口播放器遵守以下规则：

1. `playByIndex(index)` 不提前写入 `currentTrack`。
2. `playTrack()` 先完成本地 blob / 远程 URL 解析。
3. 统一执行 `pause -> audio.src -> audio.load() -> audio.play()`。
4. `audio.play()` 成功后才提交 `currentTrack/currentIndex/currentSongId`。
5. 提交后再通过 runtime 发布快照给迷你窗口。

播放资源使用 `getTrackPlaybackKey(track)` 标识：

- `local:id:path`
- `song:id`
- `cloud:id:cloudSid`
- `podcast:id:programId/rid`

迷你歌词、桌面歌词和底部控制栏歌词均按该 key 刷新，避免本地歌曲、在线歌曲、播客节目在 ID 碰撞时复用旧歌词。

## 主进程实现

### 进入迷你模式

文件：`electron/main.js`

当前逻辑：

1. 如果主窗口不存在或已处于迷你模式，则忽略
2. 记录主窗口进入迷你模式前的状态：
   - `x / y`
   - `width / height`
   - `isMaximized`
   - `wasFullScreen`
3. 创建 `miniWin`
4. 给 `miniWin` 注入 `--window-role=mini`
5. 显示并聚焦 `miniWin`
6. 隐藏 `mainWin`
7. 通知主窗口和迷你窗口当前已经处于迷你模式

### 退出迷你模式

文件：`electron/main.js`

当前逻辑：

1. 主进程收到 `mini-mode:exit`
2. 若不存在 `preMiniState`，则忽略
3. 通知主窗口和迷你窗口退出迷你模式
4. 关闭 `miniWin`
5. 按进入前保存的状态恢复 `mainWin`
6. `show()` + `focus()` 主窗口
7. 若之前是全屏或最大化，则继续恢复该状态

### 外部入口恢复主窗口

除用户点击迷你窗口关闭按钮外，某些外部入口也需要先退出迷你模式再操作主界面，例如 macOS 状态栏 Logo 菜单的「设置」。

当前统一使用 `restoreMainWindowFromMiniMode()`：

- 如果 `preMiniState` 存在，说明主窗口处于迷你模式隐藏状态
- 关闭 `miniWin`
- 清理迷你窗口置顶 / 跨桌面状态
- 恢复主窗口进入迷你模式前的 bounds / 全屏 / 最大化状态
- `show()` + `focus()` 主窗口
- 再向主窗口发送后续动作，例如 `tray-action: openSettings`

不要在托盘菜单中直接取 `BrowserWindow.getAllWindows()[0]` 或随便 `getWin()?.webContents.send('tray-action', 'openSettings')`。迷你模式下第一个窗口可能是 `miniWin`，或者主窗口仍是隐藏状态，都会导致“设置打不开 / 看不见”。

### 迷你窗口尺寸控制

迷你窗口尺寸通过 `mini-mode:resize` IPC 控制，只作用于 `miniWin`：

- 最小高度：`70`
- 最大高度：`500`
- 固定宽度：`340`（通过 `minWidth: 340` + `maxWidth: 340` 锁定）

迷你播放列表展开依然沿用原交互：

- 紧凑态：`70`（MINI_BAR_HEIGHT）
- 列表展开态：`360`（MINI_PLAYLIST_HEIGHT）

#### Windows 尺寸设置方式

为避免 Windows 上 `setSize()` 触发的尺寸提示浮层（右上角显示 `340px×70px` / `340px×360px`），所有尺寸调整操作统一使用以下模式：

1. 调高窗口为可调大小：`miniWin.setResizable(true)`
2. 使用 `miniWin.setContentSize(width, height)` 设置内容区尺寸（不会触发提示浮层）
3. 恢复不可调大小：`miniWin.setResizable(false)`

`main.js` 中涉及的两处实现：

- **`createMiniWindow()`** 创建后：移除 `...bounds` 构造参数，改为创建后使用 `setContentSize` 设置初始尺寸。解决初始窗口偏小（约 292×46）的问题，确保固定为 340×70。
- **`mini-mode:resize` IPC 处理**：将 `miniWin.setSize(340, clampedHeight)` 替换为 `setContentSize` + `setResizable` 模式。

#### MiniPlayBar.vue 中的尺寸联动

- `togglePlaylist()`：切换 `showPlaylist` 状态，调用 `syncMiniPlaylistWindow()` 根据当前状态调整窗口高度
- `syncMiniPlaylistWindow()`：`showPlaylist ? MINI_PLAYLIST_HEIGHT : MINI_BAR_HEIGHT`
- `onBeforeUnmount()`：窗口销毁前确保尺寸恢复到 70

注意：尺寸调整由 MiniPlayBar 发起请求（通过 `window.appEnv.miniMode.resize(height)`），主进程 `main.js` 实际执行窗口操作。不应跳过主进程直接操作窗口。

## 迷你窗口初始化

文件：`src/mini-main.ts`

迷你窗口当前初始化顺序：

1. 创建独立 `Pinia`
2. 初始化 `uiStore`
3. 初始化 `playerStore`
4. 初始化 `userStore`
5. 执行 `userStore.hydrate()`

迷你窗口不会在启动时执行 `userStore.refreshLoginStatus()`。

原因：

- 迷你窗口是展示 / 控制代理，不应在启动时发起第二轮登录刷新
- 主窗口已经负责完整用户态刷新
- 迷你窗口重复刷新会和首页、封面、播放详情等请求竞争，放大启动慢或封面加载慢的问题
- 收藏按钮真正点击时仍会按 `useCurrentTrackLike()` 做登录态校验

## 播放器状态与命令链路

### 当前方向

```text
主窗口 playerStore / runtime
  -> publish playback snapshot
  -> 主进程缓存 latestPlaybackSnapshot
  -> 主进程推送给 miniWin

迷你窗口 MiniPlayBar
  -> 调用 playerStore 方法
  -> mini 角色下不直接执行
  -> 转为 sendPlaybackCommand(...)
  -> 主进程转发给 mainWin
  -> mainWin 执行真实播放逻辑
```

### 关键约束

- `mini` 窗口不能直接创建 runtime
- `mini` 窗口的 `togglePlay / next / prev / playByIndex / removeFromPlaylist / openExpanded` 等行为，本质都是 IPC 命令代理
- `main` 窗口执行后再把结果以 snapshot 形式广播回来

### 当前实现注意点

播放器双窗口方案的关键风险不在“命令发不发得出去”，而在“状态是否只有一份真源”。

当前已经明确：

- 真正的播放行为由主窗口执行
- 状态广播依赖 runtime 快照
- `playerStore` 中对播放列表、当前曲目、封面、音量、播放进度等更新，必须同步到 runtime
- `miniLyricText` 属于快照里的轻量展示字段，只能由主窗口写入

这个同步链已经建立，但仍需继续验证边界路径。

## 迷你歌词链路

迷你歌词遵循“主窗口产出，迷你窗口只展示”的规则。

### 正确链路

```text
主窗口 PlayerBar.vue
  -> 复用 useLyrics() 已有歌词状态
  -> 根据 currentLyricIndex / lyricLines / 歌词设置计算 miniLyricText
  -> playerStore.setMiniLyricText(text)
  -> runtimeState / PlaybackSnapshot
  -> playback IPC
  -> 迷你窗口 MiniPlayBar.vue 读取 playerStore.state.miniLyricText
```

### 关键约束

- `MiniPlayBar.vue` 禁止调用 `useLyrics()`
- `miniWin` 禁止独立拉取歌词、解析歌词或启动歌词 tick
- 迷你歌词只是一段快照文本，不是第二套歌词系统
- 当前曲目为空时，主窗口必须产出空歌词
- 清空播放列表或删除最后一首歌时，`playerStore.state.miniLyricText` 必须同步置空

### 已修过的问题

- 迷你窗口直接调用 `useLyrics()` 曾导致 mini 渲染器黑屏，并拖慢主界面首页 / 封面加载
- `watch` 未导入曾导致迷你窗口 setup 崩溃
- 无歌词时 `v-if` 移除歌词行，导致进度条上移；当前改为固定歌词行透明占位
- 清空播放列表后歌词缓存仍保留上一首；当前通过 `currentTrack` 判空和清空队列时置空 `miniLyricText` 双保险解决

## 收藏功能链路

迷你窗口收藏按钮当前复用 `useCurrentTrackLike()`，不再维护迷你模式专用的收藏逻辑。

当前支持两类操作：

- 普通歌曲：调用 `toggleSongLike`
- 播客节目：调用 `toggleDjSubscribe`

当前鉴权行为与主界面保持一致：

- 未登录：弹登录窗
- `uid` 登录：显示“搜索用户方式登录不支持收藏功能，请使用扫码或 Cookie 登录”
- `cookie / qr` 登录：允许执行收藏 API

之前迷你模式收藏不可用的根因有两层：

1. 迷你窗口没有初始化 `userStore`
2. `useCurrentTrackLike()` 之前没有补齐统一鉴权逻辑

这部分目前已经修复到可用状态，但后续仍应继续观察主界面与迷你窗口收藏态是否始终同步。

## 已解决问题

### 1. macOS 退出迷你模式黑屏

已解决。

根因：

- 同一个 `BrowserWindow` 从迷你尺寸恢复到主窗口尺寸时，Electron/macOS 会出现表面重建黑屏

解决方式：

- 主窗口不再参与迷你尺寸切换
- 使用独立 `miniWin`

### 2. 迷你窗口关闭按钮失效

已解决。

根因：

- 迷你窗口自身 `uiStore.state.isMiniMode` 初始为 `false`
- `exitMiniMode()` 之前依赖该状态判断，导致按钮点击后没有真正发送 `mini-mode:exit`

解决方式：

- `uiStore` 按 `windowRole` 初始化迷你状态
- `mini` 角色窗口允许直接发送退出命令
- 主进程也会把 `mini-mode:state-change` 同步发给迷你窗口自身

### 3. 主界面播放状态与迷你窗口状态不一致

已部分解决，但仍需继续验证边界。

已做的修复：

- 建立 `playerStore -> runtime -> snapshot -> IPC` 链路
- `mini` 窗口只消费快照，不再直接创建播放宿主

### 4. 迷你窗口收藏功能不可用

已解决到当前阶段可用。

根因：

- 迷你窗口未恢复用户态
- 收藏 composable 缺失统一鉴权逻辑

解决方式：

- 在 `mini-main.ts` 中初始化 `userStore` 并执行本地 `hydrate()`
- 在 `useCurrentTrackLike.ts` 中补齐登录弹窗 / uid 登录提示逻辑

注意：

- 迷你窗口不再启动时调用 `refreshLoginStatus()`
- 这是为了避免独立渲染进程重复发起登录刷新，拖慢首页和封面加载

### 5. 迷你歌词显示与状态清理

已解决。

根因：

- 早期方案让迷你窗口直接调用 `useLyrics()`，相当于启动了第二套歌词加载系统
- 清空播放列表后，主窗口 `lyricLines` 可能仍保留上一首歌词缓存
- 如果 `miniLyricText` 没有随 `currentTrack` / 队列清空同步置空，迷你窗口会继续显示旧歌词

解决方式：

- 主窗口 `PlayerBar.vue` 负责计算 `miniLyricText`
- `PlaybackSnapshot` 增加 `miniLyricText`
- 迷你窗口只展示该字段
- `currentTrack` 为空时返回空歌词
- `clearPlaylist()` 和删除最后一首歌时清空 `miniLyricText`

### 6. 迷你 UI 细节问题

已解决到当前阶段可用。

已修内容：

- 无歌词时进度条会上移：改为歌词行固定占位
- 封面偏小：封面从 `36×36` 调整为 `42×42`
- 播放列表底部灰色长条：禁用横向滚动，并给列表项设置 `box-sizing: border-box`
- 关闭按钮方形 / 播放列表按钮圆形不一致：关闭按钮改为局部 `mini-close-btn`，避免被全局 `close-btn` 样式污染

### 7. 状态栏菜单打开设置不可见

已解决。

根因：

- 迷你模式下，状态栏菜单「设置」只向隐藏的主窗口发送 `openSettings`，没有先恢复主窗口
- 播放页展开时，设置页虽然被切换为 active page，但 `PlayerExpanded` 仍覆盖在上层

解决方式：

- 主进程新增 `dispatchMainWindowTrayAction('openSettings')`
- 该入口先调用 `restoreMainWindowFromMiniMode()`，确保主窗口可见并聚焦
- 渲染层 `App.vue` 的 `openTraySettings()` 先 `playerStore.closeExpanded()`，再 `openSettings('playback')`

### 8. 状态栏菜单迷你模式入口

已实现。

实现方式：

- 状态栏 Logo 菜单根据 `preMiniState` 显示「打开迷你模式」或「关闭迷你模式」
- 打开时调用主进程 `enterMiniMode(false)`，复用和渲染层 `mini-mode:enter` 相同的双窗口链路
- 关闭时调用 `restoreMainWindowFromMiniMode()`，复用已有主窗口恢复逻辑
- 菜单状态在进入 / 退出迷你模式后通过 `setTrayMenu(win)` 重建，避免显示旧状态

## 播放页打开动画设置

播放页展开/收起动画已支持用户在设置页选择。

入口：

- 设置页 → 外观 → 播放页打开动画

状态存储：

- `uiStore.state.playerPageTransition`
- localStorage key：`tm_player_page_transition`
- 默认值：`幕布揭开`

当前可选项：

| 选项 | transition name | 效果 |
|---|---|---|
| `经典上滑` | `player-sheet` | 经典体验：整体淡入缩放，内容从底部上滑 |
| `景深推进` | `player-depth` | 播放页从景深中推进，带轻微 blur / scale |
| `液态扩散` | `player-liquid` | 背景光晕式扩散，内容柔和浮入 |
| `幕布揭开` | `player-curtain` | 使用 `clip-path` 从底部揭开播放页 |

实现位置：

- `src/stores/ui.ts`：定义 `PlayerPageTransition`、读取/保存用户偏好
- `src/components/SettingsPage.vue`：外观设置下拉项
- `src/components/PlayerExpanded.vue`：根据 `uiStore.state.playerPageTransition` 动态选择 `<transition :name="playerTransitionName">`

约束：

- 动画只影响播放页外层进入/退出，不改变播放状态
- 保留 `prefers-reduced-motion: reduce` 降级，用户系统设置减少动态效果时只保留轻量 opacity 过渡
- 后续如果实现“封面源点放大”，需要额外测量底部控制栏封面坐标，不建议和当前 CSS-only 方案混在同一批风险里

## 后续修复建议

后续继续修 bug 时，建议按下面顺序推进：

1. 先守住双窗口架构，不要回退到单窗口缩放方案
2. 所有播放相关 bug 先查“命令链”和“快照链”
3. 明确区分：
   - 主窗口：执行者
   - 迷你窗口：观察者 + 控制代理
4. 新增功能时优先检查是否会创建第二份播放宿主
5. 新增迷你展示字段优先走 `PlaybackSnapshot`，不要在迷你窗口重复请求业务数据
6. 涉及清空播放状态时，同时检查迷你窗口展示字段是否需要置空
7. 外部入口需要打开主界面页面时，必须先恢复主窗口，再关闭可能覆盖页面的播放页

## 结论

当前迷你模式已经进入“架构切换完成，功能继续收口”的阶段。

可以明确确认的事实是：

- 迷你模式不是新 UI 设计
- 当前 UI 规格保持原样
- 双窗口方案已经替代旧单窗口方案
- macOS 退出迷你模式黑屏问题已经通过架构调整解决
- 迷你歌词、进度条固定、封面尺寸、播放列表横向滚动条、旧歌词清理等近期问题已经收口
- 状态栏菜单「设置」在迷你模式和播放页状态下不可见的问题已经收口
- 剩余风险主要集中在播放状态同步和特殊入口边界，不在窗口切换主路径本身
