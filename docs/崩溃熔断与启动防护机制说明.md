# 崩溃熔断与启动防护机制说明

## 背景

Resound-Player 桌面端在 macOS 上首次打包发布后，出现"无限自启"问题：应用打开后立即崩溃，macOS launchd 检测到异常退出后自动重启应用，形成崩溃→重启→崩溃的循环，严重时可能导致系统资源耗尽。

通过排查发现两层问题：一是打包产物的直接异常；二是 Electron 子进程的错误启动方式导致进程爆炸式增长。本文件记录所有修复措施和防护机制的实现。

后续继续排查时又确认了一层真实问题：即使主进程本身可启动，打包后的本地 API / unblock 服务如果从错误的解包路径直接运行，也会因为依赖解析失败而表现为“45 秒内 API 未就绪”。这属于**启动链成功进入 JS 之后的服务装配问题**，已和本文件中的前置崩溃问题区分修复。

## 一、熔断核心机制

### 1.1 整体架构

```
应用启动
  │
  ├─ 模块加载时 → earlyFuseLockCheck() ← 熔断锁提前检测
  │     ├─ 文件存在 → process.exit(0)  ← 立即退出，不启动 Electron
  │     └─ 文件不存在 → 继续正常启动
  │
  └─ app.whenReady() → bootstrap()
        │
        ├─ checkCrashCircuitBreaker() ← 崩溃计数器检测
        │     ├─ 无标记 → 写 count=1 → 放行
        │     ├─ 窗口过期 → 重置 count=1 → 放行
        │     ├─ count < 3 → count+1 → 放行
        │     └─ count ≥ 3 → writeFuseLock() → 触发熔断 → 显示错误窗口
        │
        ├─ 递归防护锁 (_bootstrapInProgress/_bootstrapCompleted)
        ├─ 启动服务 / 等待 API
        ├─ 创建主窗口
        └─ 正常退出 → will-quit → clearCrashMarker()
```

### 1.2 关键常量

| 常量 | 值 | 说明 |
|---|---|---|
| `CRASH_THRESHOLD` | 3 | 60 秒内连续崩溃阈值 |
| `CRASH_WINDOW_MS` | 60000 (60s) | 崩溃计数时间窗口 |

### 1.3 两种标记文件

#### 崩溃标记 (crash-marker.json)

- **路径**: `~/Library/Application Support/Resound-Player/crash-marker.json`
- **内容**: `{ "count": number, "firstCrashAt": timestamp }`
- **生命周期**: 应用正常退出时自动清除
- **用途**: 统计时间窗口内连续崩溃次数

#### 熔断锁 (crash-fuse.lock)

- **路径**: `~/Library/Application Support/Resound-Player/crash-fuse.lock`
- **内容**: `{ "triggeredAt": timestamp, "message": "应用因连续崩溃被熔断锁锁定" }`
- **生命周期**: 永不自动删除，需用户手动清理
- **用途**: 触发熔断后永久阻止应用启动，直至用户确认问题

### 1.4 工作流程

```
正常启动 → crash-marker: count=1
   ↓ (异常退出/crash)
macOS launchd 自动重启 → crash-marker: count=2 (60s 窗口内)
   ↓ (再次 crash)
macOS launchd 自动重启 → crash-marker: count=3 → ⛔ 熔断触发
   ↓
writeFuseLock() 写入永久熔断锁 → createErrorWindow() 显示错误窗口
   ↓ 用户关闭窗口 → app.quit() → will-quit 清理 crash-marker (保留 fuse lock)
   ↓
macOS 感知到整洁退出 → 停止自动重启
   ↓ 用户下次手动启动
earlyFuseLockCheck() 检测到 fuse lock → process.exit(0) 立即退出
   ↓
用户按提示执行 rm -f crash-fuse.lock → 应用恢复正常启动
```

### 1.5 实现文件

**`electron/main.js`**:

| 函数/模块 | 职责 |
|---|---|
| `userDataDir()` | 获取应用数据目录路径（`~/Library/Application Support/Resound-Player`） |
| `crashMarkerPath()` | 崩溃标记文件路径 |
| `fuseLockPath()` | 熔断锁文件路径 |
| `readCrashMarker()` | 读取崩溃标记 |
| `writeCrashMarker(count, firstCrashAt)` | 写入崩溃标记 |
| `clearCrashMarker()` | 清除崩溃标记 |
| `writeFuseLock()` | 写入熔断锁（熔断触发时调用） |
| `checkFuseLockExists()` | 检测熔断锁是否存在 |
| `clearFuseLock()` | 清除熔断锁 |
| `earlyFuseLockCheck()` | 模块加载时立即执行，检测到熔断锁则 `process.exit(0)` |
| `checkCrashCircuitBreaker()` | 启动前检查崩溃计数器，决定是否放行或熔断 |
| `_bootstrapInProgress` | 递归防护锁 — bootstrap 正在执行 |
| `_bootstrapCompleted` | 递归防护锁 — bootstrap 已完成 |
| `_circuitBreakerTripped` | 熔断器已触发标记 |

## 二、启动循环递归防护

### 2.1 三态锁

```typescript
let _bootstrapInProgress = false;    // bootstrap 正在执行中
let _bootstrapCompleted = false;     // bootstrap 已完整结束
let _circuitBreakerTripped = false;  // 熔断器已触发
```

`bootstrap()` 入口处检查三态锁：

```typescript
// 熔断检查
if (!checkCrashCircuitBreaker()) {
  _circuitBreakerTripped = true;
  await createErrorWindow(...);
  return;
}
// 递归防护
if (_bootstrapInProgress) { console.warn('跳过重复调用'); return; }
if (_bootstrapCompleted) { console.warn('跳过重复调用'); return; }
_bootstrapInProgress = true;
```

### 2.2 activate 事件防护

macOS 点击 Dock 图标会触发 `activate` 事件。原始代码在该事件中直接调用 `bootstrap()`，若 bootstrap 因异常提前返回（未设置 `_bootstrapCompleted = true`），再次点击 Dock 会触发新的 bootstrap 实例。

**修复后的逻辑**：

```typescript
app.on('activate', () => {
  if (_circuitBreakerTripped) { return; }
  if (_bootstrapInProgress) { return; }
  if (_bootstrapCompleted) {
    // 仅重建窗口，不重启服务
    createMainWindow(ports);
    return;
  }
  // 从未启动过 → 首次启动
  bootstrap();
});
```

### 2.3 will-quit 状态感知

正常退出时清除崩溃标记，但熔断状态下仅清标记不清锁：

```typescript
app.on('will-quit', () => {
  if (_circuitBreakerTripped) {
    console.log('[main] 熔断态退出，保留熔断锁');
  } else {
    console.log('[main] 正常退出，清除崩溃标记');
  }
  clearCrashMarker();
  killAllServices(serviceChildren);
});
```

### 2.4 未捕获异常处理

保留崩溃标记，确保下次启动时计数器递增：

```typescript
process.on('uncaughtException', (err) => {
  console.error('[main] 未捕获异常:', err);
  setImmediate(() => process.exit(1));
});

process.on('unhandledRejection', (reason) => {
  console.error('[main] 未处理的 Promise 拒绝:', reason);
});
```

## 三、崩溃放大根因修复

### 3.1 问题描述

`electron/serviceManager.js` 中，`spawnUnblockProxy()` 在 `spawn` 时缺少 `ELECTRON_RUN_AS_NODE: '1'` 环境变量。由于 `process.execPath` 指向 Electron 二进制文件，不带 `ELECTRON_RUN_AS_NODE` 的 spawn 会启动全新的 Electron 实例（而非运行指定脚本），每个新实例又执行 `main.js`，再次 spawn 更多子进程，导致进程指数级增长，最终系统崩溃。\n\n> 注：`spawnUnblockMatch()` 已在后续版本中移除，match 能力已收敛到 Electron 主进程内部。

### 3.2 修复

```diff
// electron/serviceManager.js - spawnUnblockProxy()
env: {
  ...process.env,
+ ELECTRON_RUN_AS_NODE: '1',   // ← 新增
  ENABLE_FLAC: 'true',
  NODE_ENV: 'production',
},

// electron/serviceManager.js - spawnUnblockMatch()
env: {
  ...process.env,
+ ELECTRON_RUN_AS_NODE: '1',   // ← 新增
  PORT: String(port),
  UNBLOCK_PROXY_URL: `http://127.0.0.1:${unblockProxyPort}`,
  UNBLOCK_SOURCES: 'bodian,kugou,migu,qq,bilibili',
},
```

**验证方式**：子进程日志从 `[unblock-proxy] [main] 应用启动中...`（加载了 main.js）变为直接运行目标脚本，不再输出 `[main]` 前缀日志。

## 四、Electron 版本兼容修复

### 4.1 registerFileProtocol → protocol.handle

Electron 28+ 移除了 `protocol.registerFileProtocol` API。打包使用的 Electron 版本为 34+，调用该 API 时会抛出 `TypeError`。

```diff
- protocol.registerFileProtocol('local', (request, callback) => { ... });
+ protocol.handle('local', (request) => {
+   // ...
+   return net.fetch('file://' + filePath);
+ });
```

同时引入 `net` 模块：

```diff
- import { app, BrowserWindow, Menu, ipcMain, protocol } from 'electron';
+ import { app, BrowserWindow, Menu, ipcMain, protocol, net } from 'electron';
```

### 4.2 require → await import (ESM 兼容)

ESM 模式下 `require` 不可用，菜单 click 回调中使用 `require('electron')` 会抛 `ReferenceError`：

```diff
- click: () => {
-   const { dialog } = require('electron');
+ click: async () => {
+   const { dialog } = await import('electron');
```

## 五、安全与进程防护（Electron 规范整改）

### 5.1 单实例锁

防止用户误触多开导致数据冲突或端口占用：

```javascript
// main.js — 在 app.whenReady() 前执行
const gotTheLock = app.requestSingleInstanceLock();
if (!gotTheLock) {
  app.quit();
}

// 第二实例聚焦已有窗口
app.on('second-instance', () => {
  const windows = BrowserWindow.getAllWindows();
  if (windows.length > 0) {
    const mainWin = windows[0];
    if (mainWin.isMinimized()) mainWin.restore();
    mainWin.focus();
  }
});
```

### 5.2 Content-Security-Policy

生产环境注入 CSP 头，限制脚本和连接来源，防止 XSS → RCE：

```javascript
if (app.isPackaged) {
  win.webContents.session.webRequest.onHeadersReceived((details, callback) => {
    callback({
      responseHeaders: {
        ...details.responseHeaders,
        'Content-Security-Policy': [
          "default-src 'self'",
          "script-src 'self' 'unsafe-inline'",
          "style-src 'self' 'unsafe-inline'",
          "connect-src 'self' http://127.0.0.1:* blob: data:",
          "img-src 'self' data: blob: http://* https://*",
          "media-src 'self' blob: http://127.0.0.1:*",
          "font-src 'self' data:",
        ].join('; '),
      },
    });
  });
}
```

### 5.3 生产环境禁用开发者工具

```javascript
webPreferences: {
  devTools: !app.isPackaged,
}
```

### 5.4 导航与弹窗拦截

```javascript
win.webContents.on('will-navigate', (event, url) => {
  const allowed = [
    'file://' + path.join(__dirname, '..', 'dist', 'index.html'),
    process.env.VITE_DEV_SERVER_URL || '',
  ].filter(Boolean);
  if (!allowed.some((a) => url.startsWith(a))) {
    event.preventDefault();
  }
});

win.webContents.setWindowOpenHandler(({ url }) => {
  return { action: 'deny' };
});
```

### 5.5 GPU 进程崩溃降级

```javascript
win.webContents.on('gpu-process-crashed', (_event, killed) => {
  app.commandLine.appendSwitch('disable-gpu');
  app.relaunch();
  app.exit(0);
});
```

### 5.6 IPC 文件读取路径校验

防止渲染进程通过 `local:read-file` 等 IPC 进行路径穿越攻击：

```javascript
function isPathSafe(requestedPath) {
  const normalized = path.resolve(requestedPath);
  const blockedPrefixes = ['/etc', '/var', '/System'].map(p => path.resolve(p));
  for (const prefix of blockedPrefixes) {
    if (normalized.startsWith(prefix)) return false;
  }
  if (normalized.includes('/../')) return false;
  return true;
}
```

应用到 `local:get-lyric`、`local:get-cover`、`local:read-file` 三个 handler。

## 六、ASAR 打包与 pnpm 兼容

### 6.1 asar: true

生产环境启用 ASAR 打包，防止源码直接暴露。asarUnpack 需覆盖 pnpm 符号链接结构和子进程依赖：

```json
{
  "asar": true,
  "asarUnpack": [
    "node_modules/.pnpm/@neteasecloudmusicapienhanced+api@*/**/*",
    "node_modules/.pnpm/@unblockneteasemusic+server@*/**/*",
    "node_modules/.pnpm/@neteasecloudmusicapienhanced+unblockmusic-utils@*/**/*",
    "node_modules/@neteasecloudmusicapienhanced/**/*"
  ]
}
```

### 6.2 pnpm 路径解析修复

`serviceManager.js` 中 `resolveApiEntrypath()` 使用 `isFile(pnpmDir)` 检查 `.pnpm` 目录，但 `.pnpm` 是目录而非文件，导致路径解析永远无法进入 pnpm 分支：

```diff
- if (isFile(pnpmDir)) {
+ function isExists(p) { try { return fs.existsSync(p); } catch { return false; } }
+ if (isExists(pnpmDir)) {
```

配合 `asarUnpack` 将 `.pnpm` 存储中的 API 模块解包到 `app.asar.unpacked/`，子进程可正确读取文件。

### 6.3 打包后服务真实启动修复

后续实测发现，单纯把目录解包到 `app.asar.unpacked` 还不够，两个服务仍可能因为“从散文件入口启动”而丢失依赖：

- `@neteasecloudmusicapienhanced/api` 从 `app.asar.unpacked/.../api` 直接跑时，模块内继续 `require('axios')` 等依赖，向上找不到完整包层级
- `@unblockneteasemusic/server` 生产模式会 `require('../../precompiled/app')`，如果把 `precompiled/**` 排除在打包外，服务会直接启动失败

最终修复方案：

1. API package root 解析优先使用 `app.asar/node_modules/@neteasecloudmusicapienhanced/api`
2. 仅在找不到真实包根时，才回退到 `app.asar.unpacked`
3. `Netease API` 与 `Unblock Proxy` 均改为 `node -e <bootstrap>` 方式启动
4. bootstrap 内通过包根 `require()` 真正入口，而不是直接执行解包散文件
5. 恢复保留 `@unblockneteasemusic/server/precompiled/**` 打包内容

这样打包后的桌面端可以稳定拉起：

- `Netease API` on `127.0.0.1:38761`
- `Unblock Proxy` on `127.0.0.1:38762`
- `Unblock Match` — 生产模式由 Electron 主进程内置 native bridge 处理（`unblock-native-match.js`），不再启动外部 match 子进程。开发模式下 `start-desktop.mjs` 仍会启动外部 match 服务作为 fallback。

### 6.4 API 健康检查修正

此前 `waitApiReady()` 使用 `/banner` 作为健康检查端点，这会带来误判：

- `/banner` 依赖远端网易接口
- 本地 API 服务已经启动，但上游暂时异常时，健康检查仍会失败
- 主进程因此错误提示“API 服务未能在 45 秒内就绪”

现在已改为检测 `GET /`：

- 只判断本地 API 进程是否真的在监听
- 不把远端接口瞬时波动误判为本地服务启动失败

### 6.5 mac 本地构建后的 bundle 修复

实测 electron-builder 在本机无正式证书时，可能产出签名状态异常的 `.app`：

- `Identifier=Electron`
- `Info.plist=not bound`
- `Sealed Resources=none`

这类 bundle 可能在 Finder 启动阶段就崩溃，甚至在主进程 JS 顶层日志落盘前退出。

当前本地 mac 构建脚本已补充后处理：

```bash
xattr -cr dist-build/mac-arm64/Resound-Player.app
codesign --force --deep --sign - --timestamp=none dist-build/mac-arm64/Resound-Player.app
codesign --verify --deep --strict --verbose=2 dist-build/mac-arm64/Resound-Player.app
```

作用：

- 清理扩展属性污染
- 生成稳定可启动的本地 ad-hoc 签名
- 让本地测试包与实际安装测试路径保持一致

## 九、应急处理

### 9.1 用户端清理命令

当熔断锁触发后，用户需执行以下命令解锁：

```bash
rm -f ~/Library/Application\ Support/Resound-Player/crash-fuse.lock
```

### 9.2 完整重置

如需彻底清除所有崩溃状态：

```bash
rm -f ~/Library/Application\ Support/Resound-Player/crash-*.json
rm -f ~/Library/Application\ Support/Resound-Player/crash-*.lock
```

### 9.3 应用数据目录

```
~/Library/Application Support/Resound-Player/
  ├── crash-marker.json     ← 崩溃计数器（自动管理）
  ├── crash-fuse.lock       ← 熔断锁（需手动清理）
  ├── api-cache.json        ← API 缓存
  └── LocalMusicDB/         ← 本地音乐数据库
```
